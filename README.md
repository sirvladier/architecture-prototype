# Объяснимое формирование рекомендаций при выборе архитектуры

Локальный исследовательский прототип на Python 3.12. Программа сравнивает только
A1 (монолит), A2 (SOA) и A3 (микросервисы) по структурированным данным.
Используются обязательные ограничения и взвешенная сумма оценок. LLM, нейросети,
обработка естественного языка, внешние API и базы данных не используются.

**Все исходные архитектурные оценки, свойства, веса, пороги и тексты рисков
в комплекте являются PLACEHOLDER / MODEL VALUES. Это параметры синтетической
модельной постановки, а не универсальные нормативные или экспертные значения.**
Статус `confirmed` у синтетической оценки означает фиксированное значение
в техническом примере, а не эмпирическое подтверждение свойства архитектуры.

## Установка и запуск

Для этой копии подготовлено окружение `.venv` с Python 3.12.13.
Все команды ниже выполняются в PowerShell из каталога проекта:

```powershell
Set-Location 'E:\статья'
.\.venv\Scripts\python.exe -m streamlit run app.py --server.address 127.0.0.1 --server.port 8501
```

Адрес по умолчанию: http://127.0.0.1:8501. Если порт занят, задайте свободный
через `--server.port`. Приложение слушает только локальный адрес.
Сбор статистики Streamlit отключён в `.streamlit/config.toml`.

Для установки в новом каталоге с уже установленным Python 3.12:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Прямые зависимости закреплены: Streamlit 1.45.1, pandas 2.2.3, numpy 2.2.5,
pytest 8.3.5. Сеть нужна для установки; расчёты выполняются локально.

```powershell
# Автоматические тесты, включая Streamlit AppTest
.\.venv\Scripts\python.exe -m pytest -q

# Технический эксперимент по всем модельным кейсам

# Другой файл результатов
.\.venv\Scripts\python.exe -m src.experiment --output data\repeat_results.csv
```

Если системный временный каталог недоступен, тесты можно запустить с новым
временным каталогом внутри проекта:

## Режимы и пользовательский сценарий

В боковой панели выбирается «Модельный кейс» или «Пользовательский кейс».
Первый режим загружает готовые синтетические примеры с их статусами данных;
они сохранены для демонстрации, тестов и технического эксперимента.

В пользовательском режиме задаются только значимости критериев и обязательные
требования проекта. Оценки архитектур, их свойства, направления критериев,
правила рисков и статусы данных пользователь не редактирует. Таблица
«Параметры модели» и подробные статусы доступны только для чтения.

Последовательность работы:

1. Выбрать «Пользовательский кейс».
2. Ввести неотрицательную значимость каждого критерия. Рядом показаны введённые
   значения и нормированные веса; все нулевые веса запрещены.
3. Добавить обязательные требования: выбрать свойство по русскому названию,
   условие и требуемое значение. Название требования можно изменить,
   ненужное требование удалить. Внутренние ID вводить не требуется.
4. Нажать «Сформировать рекомендацию». Вызывается существующее ядро:
   валидация, ограничения, рейтинг, объяснение и чувствительность.
5. Открыть «Сравнение», затем «Объяснение» и выбрать P1/P2/P3.
6. Посмотреть раздельные точки tie и switch на вкладке чувствительности.

Изменение поля обновляет только состояние ввода и предварительную нормировку,
не запускает полный расчёт. До нажатия кнопки результатов нового кейса нет.
Если входы изменены после расчёта, старые результаты и скачивание скрываются,
пока новые данные не рассчитаны. Переключение P1/P2/P3 не пересчитывает рейтинг.
Ввод и рассчитанный пользовательский кейс сохраняются при смене режима в том
же сеансе браузера. Постоянное хранилище не используется.

«Скачать исходные данные кейса» сохраняет JSON последнего соответствующего
вводу расчёта: исходные веса, нормированные веса, ограничения, SHA-256
конфигурации архитектур и всей модели. Это идентификаторы содержимого,
не произвольно заданные версии. «Результат JSON» сохраняет полный
ExplanationData с входным снимком. Обратной загрузки JSON через UI нет.

`UserCase` в `src/user_cases.py` допускает только `weights` и `constraints`.
Передача `ratings`, `architectures`, `risks`, `criteria` или `settings`
отклоняется. `build_user_model` самостоятельно загружает архитектурные
оценки из конфигурации, преобразует требования в существующий формат
`constraints.py` и передаёт результат общей функции `build_explanation`.
Новой формулы выбора или отдельных вычислений для пользовательского режима нет.

## Конфигурация

JSON-файлы читаются как UTF-8. Изменение оценок, весов, направлений,
ограничений и рисков не требует редактирования Python-кода. Идентификаторы
архитектур фиксированы: A1, A2, A3; критериев: K1..K6.

### architectures.json

`architectures` содержит `id`, `name`, `ratings`, `properties`, `risk_ids`.
`ratings` сопоставляет ID критерия со структурированной оценкой:

```json
{"value": 4, "status": "estimated"}
```

Значения, включая дробные, должны лежать в [1, 5]. Допустимые статусы:
`confirmed`, `estimated`, `missing`. Пропуск задаётся отдельно от подстановки:

```json
{"value": null, "status": "missing", "model_value": 4}
```

`properties` хранит свойства для ограничений. Числовые и категориальные
свойства из комплекта также являются синтетическими. `risk_ids` связывает
архитектуру с её правилами из `risks.json`; несогласованные ссылки запрещены.

### criteria.json

У каждого критерия заданы `id`, `key`, русские `name` и `description`,
`direction`, `weight`. Вес должен быть конечным неотрицательным числом;
хотя бы один вес положителен. Перед расчётом веса нормируются до суммы 1.

Направление всегда читается из конфигурации, отдельно для каждого критерия:

- `maximize`: полезность `value / 5`;
- `minimize`: полезность `(6 - value) / 5`.

Обе формулы дают [0.2, 1] на шкале 1..5; оценка `score` тем самым находится
в требуемом диапазоне [0, 1]. При `minimize` меньшая исходная оценка лучше.
В исходном комплекте K6 означает экономичность, поэтому задан `maximize`.
При другой интерпретации параметра измените описание и направление вместе.

`contribution(a, i) = normalized_weight_i * utility(a, i)`.
`score(a)` равен сумме вкладов. В расчёте используются неокруглённые числа;
округление в таблицах служит только для отображения.

В `settings` находятся технические правила:

- `tie_policy: "tie"`: единственный победитель при равенстве не выбирается.
- `tie_tolerance`: абсолютный допуск сравнения итоговых баллов.
  Лидеры в пределах допуска от максимума входят в `winners`.
- `top_factor_count`: число положительных и число отрицательных факторов.
- `missing_policy: "model_or_block"`: использовать только явно указанное
  `model_value`; иначе остановить рейтинг со статусом `insufficient_data`.
- `missing_policy: "block"`: пропуск блокирует рейтинг даже при наличии
  `model_value`.
- `sensitivity.step`: шаг изменения нормированного веса, от 0.0001 до 1.
  Нижний технический предел ограничивает объём дискретного перебора.
- `sensitivity.min_weight`, `max_weight`: исследуемый диапазон внутри [0, 1].
- `sensitivity.zero_remainder_policy`: `uniform` распределяет остаток поровну
  между другими критериями при исходном весе 1; `skip` пропускает такое
  направление и помечает исследование как частичное. Пропорциональное
  распределение между исходными нулевыми весами не определено.

### constraints.json

`properties` содержит каталог уже существующих свойств для интерфейса:
внутреннее `property`, русское `name`, тип `boolean` / `numeric` / `categorical`.
Для категорий `value_labels` задаёт отображаемые названия значений.
Каталог не меняет архитектурные свойства, пороги или правила исключения.
В пользовательском режиме обязательные требования формируются из ввода
проекта; демонстрационные правила `constraints` автоматически не добавляются.

В `constraints` каждое правило имеет `id`, `name`, `enabled`, `property`,
`type` и параметры соответствующего типа:

| Тип | Параметр | Проверка |
| --- | --- | --- |
| boolean | expected | точное логическое равенство |
| numeric_min | threshold | свойство >= threshold |
| numeric_max | threshold | свойство <= threshold |
| categorical | allowed_values | строковое свойство входит в список |

Отсутствующее свойство и несоответствующий тип считаются нарушением.
`true` не подменяет число 1 при числовой проверке. Все нарушения сохраняются
с ID, фактическим значением, оператором и ожидаемым значением.
Исключённые альтернативы не участвуют ни в рейтинге, ни в чувствительности.
Если исключены все, возвращается `no_feasible`.

### risks.json

`risks` содержит только явные правила: `id`, `architecture`, `criterion`,
`operator`, `threshold`, `text`. `architecture` использует A1/A2/A3,
`criterion` использует K1..K6. Операторы: `<`, `<=`, `>`, `>=`, `==`, `in`.
Для `in` порог является списком чисел, для остальных операторов числом.

Условия применяются к исходной оценке 1..5, фактически выбранной для расчёта,
а не к её направленной полезности или взвешенному вкладу. Смена `direction`
не меняет смысл оператора риска. При модельной подстановке риск сохраняет
`data_status: "missing"` и `model_value_used: true`.
В объяснение входят риски только единственной рекомендованной архитектуры.
При отсутствии единственного победителя список рисков рекомендации пуст.

### example_cases.json

Все кейсы помечены `SYNTHETIC / MODEL CASES`. Поля:
`id`, `name`, необязательные `description`, `weights`, `ratings`,
`enabled_constraints`, `constraint_overrides`, `expected`.
`weights`, если заданы, должны содержать все шесть критериев.
`ratings` заменяет целую структуру конкретной оценки, поэтому прежнее
`model_value` не переносится в новый пропуск незаметно.
`enabled_constraints` задаёт полный список активных ограничений для кейса.
`constraint_overrides` меняет только параметры условий.
`expected` содержит технические ожидания теста, а не экспертные оценки.

## Неопределённость и объяснение

`uncertain_data` содержит все `estimated` и `missing`, включая данные
исключённых альтернатив. Для каждой записи сохраняются `architecture`,
`criterion`, `status`, `original_value`, `model_value`, `used_value`,
`model_value_used`, `source`, `architecture_is_feasible`, `used_in_ranking`.
Разрешение значения и участие в рейтинге различаются: исключённая
альтернатива не ранжируется. При остановке из-за пропусков рейтинг вообще
не вычисляется, и `used_in_ranking` у всех записей равно `false`.

Все шесть оценок каждой допустимой альтернативы обязательны, даже при
нулевом исходном весе: анализ чувствительности может увеличить этот вес.
Пропуски исключённых альтернатив не блокируют расчёт допустимых.
`based_on_incomplete_data` отмечает пропуски среди допустимых альтернатив,
включая случай блокировки. `has_uncertain_data` учитывает и `estimated`.
P3 отдельно показывает исходное значение, модельную подстановку и её статус.

Причины исключения не используются как факторы предпочтения.
Факторы сравнивают победителя с ближайшим допустимым конкурентом по разности
вкладов. Положительные сортируются по убыванию, отрицательные по возрастанию
(наиболее сильная слабая сторона первой). При равных разностях используется ID.
Если конкуренты равны в пределах допуска, `runner_up_candidates` хранит их
всех; для конкретных разностей берётся первый по порядку балл по убыванию,
ID по возрастанию. Этот выбор явно отображается. При одной допустимой
альтернативе сравнения с конкурентом нет.

`ExplanationData` создаётся один раз на набор входов. В Streamlit он хранится
в состоянии сеанса. Переключение P1/P2/P3 вызывает только функции слоя
представления и форматтеры:

- P1: рекомендация, рейтинг, статусы исключённых.
- P2: P1, причины исключения, положительные факторы и слабые стороны.
- P3: P2, формальные риски, неопределённость, чувствительность.

P2 содержит отдельный блок «Почему сформирована эта рекомендация».
Форматтер `src/p2_format.py` читает готовый `ExplanationData`, использует
полные названия архитектур и критериев, отдельно формулирует причины
исключения и сравнение с ближайшей допустимой альтернативой. Он не меняет
объект результата и не запускает вычислительное ядро.

В текстовом резюме показывается не более трёх преимуществ и трёх слабых
сторон, упорядоченных по абсолютной разности вкладов. В таблицах сохраняются
все факторы, переданные существующим расчётным ядром; его настройка
`top_factor_count` не изменяется. Дополнительная таблица показывает готовые
вклады всех критериев допустимых альтернатив. Числа форматируются до четырёх
знаков после запятой только при отображении; исходная точность сохраняется.

При равенстве P2 сообщает об отсутствии однозначной рекомендации, при
исключении всех альтернатив показывает причины исключения, а единственную
допустимую альтернативу объясняет результатом проверки ограничений.
Фиктивные сравнения в этих случаях не создаются. Риски, статусы достоверности
и чувствительность в P2 не включаются. Случай исходного равенства в P2
не следует путать с анализом точек tie/switch, который остаётся в P3.

P3 повторно использует существующее отображение P2 без отдельного расчёта.
После него следуют блоки «Риски, неопределённость и устойчивость», «Риски»,
«Неопределённость и пропуски» и «Чувствительность рекомендации».
Человекочитаемый текст формируется функцией `format_p3(ExplanationData)`
из `src/p3_format.py`. Расчётный объект и прежний программный интерфейс
`presentation` сохраняются без изменений.

В резюме чувствительности показано максимум три ближайших события из
существующих `nearest_tie_weight` и `nearest_switch_weight`. События
сортируются по абсолютному изменению относительно исходного веса; равные
изменения упорядочиваются по ID критерия, затем потеря однозначности перед
сменой рекомендации. Новые точки не рассчитываются. Разные направления
не объединяются в вымышленную последовательность.

Веса в основном тексте и краткой таблице показаны в процентах с одним
знаком после запятой. Используются полные названия архитектур и критериев.
Модельная подстановка описывается явно и не называется подтверждённым
исходным значением. Для исключённых альтернатив или остановленного расчёта
не утверждается, что их значения использовались при выборе.
При нескольких неопределённых значениях резюме содержит количество,
подробности перечислены ниже.

Правила риска, статусы достоверности и исходные значения остаются в закрытых
блоках «Подробные данные о рисках» и «Подробные данные о неопределённости».
Большая таблица по обоим направлениям и исходная структура чувствительности
сохранены в закрытом блоке «Подробный анализ чувствительности». В технических
таблицах числовое отображение ограничено четырьмя знаками; исходные значения
в `ExplanationData` и выгрузке JSON не округляются.

При равенстве, нехватке данных, исключении всех альтернатив или частично
проверенном диапазоне текст отражает соответствующий статус. Отсутствие
событий относится только к исследованной сетке и не означает абсолютной
устойчивости. Округление процентов служит для чтения; близкие события могут
выглядеть одинаково в основном тексте, а подробные данные сохраняют различие.

Вкладка «Сравнение» дополнительно показывает нормированные веса и вклады.
В пользовательском режиме изменения применяются кнопкой
«Сформировать рекомендацию». Переключение модельного кейса загружает его
собственные исходные значения. Оценки архитектур, направления критериев
и правила рисков редактируются исследователем только в JSON.
Полный объект можно выгрузить кнопкой
«Результат JSON». `calculation_id` является SHA-256 входного снимка;
он позволяет проверить, что представления относятся к одному расчёту.

## Чувствительность

Для каждого критерия перебираются веса `w +/- n * step` в заданном диапазоне.
Границы включаются, даже если не кратны шагу. Остальные веса изменяются
пропорционально своим исходным нормированным значениям; их сумма равна
`1 - new_weight`. Ограничения, оценки, направления и риски не изменяются.

Поиск проходит весь диапазон в обе стороны и сохраняет два разных события:

- `nearest_tie_weight`, `tie_delta`, `tie_signed_delta`, `tie_winners`:
  ближайшее равенство лидеров, то есть отсутствие единственного победителя;
- `nearest_switch_weight` (также `switch_weight`), `delta`, `signed_delta`,
  `new_winner`: ближайшее появление другого единственного победителя.

`delta` и `tie_delta` неотрицательны; поля `signed_delta` сохраняют знак.
При равноудалённых событиях выбирается меньший вес. `directions` сохраняет
отдельные события уменьшения и увеличения, число и границы проверенных точек.
Поиск tie продолжается и после switch: ближайшее равенство может возникнуть
уже между другими лидирующими альтернативами, что видно из `tie_winners`.

Если событие не найдено, его вес и расстояние равны `null`.
`stable_sampled` означает отсутствие и switch, и tie на исследованной сетке.
`tie_found` означает найденную потерю однозначности без другого единственного
победителя. При этом `no_switch_in_explored_range=true`, но
`unique_winner_preserved=false` и `stable_in_explored_range=false`.
Проверенный частично диапазон не называется устойчивым.
Если исходный вес вне диапазона, возвращается `original_outside_range`.
Если исходно нет единственного победителя, возвращается
`not_applicable_*`: смена единственного победителя от такой базы не определена.

Это дискретный, а не аналитический поиск: точка равенства или смены между
узлами сетки может быть пропущена. `null` не доказывает устойчивость на всём
непрерывном интервале. Уменьшение шага повышает разрешение проверки.
Произвольные словесные категории устойчивости не используются.

## Эксперимент и воспроизводимость

Режим `python -m src.experiment` создаёт CSV с требуемыми счётчиками,
`nearest_sensitivity_delta`, `validation_passed`, а также `nearest_tie_delta`,
статусом, признаком неполноты, хешем входов и ошибками валидации.
CSV записывается в UTF-8 с BOM для открытия в табличных редакторах.
Рядом сохраняется JSON со всеми объяснениями и полными входными снимками.

Валидация повторяет расчёт из снимка, сверяет рейтинг, исключения, вклады,
факторы, риски и неопределённость; отдельно пересчитывает заявленные tie
и switch; проверяет согласованность P1/P2/P3 и ожидания кейсов.
Автотесты дополнительно проверяют известные вручную вычисленные суммы,
направления предпочтения, нормировку, все типы условий, обе стороны
чувствительности, раздельность tie/switch и интерфейс Streamlit.

`validation_passed=true` означает успешную техническую проверку, в том числе
ожидаемый `tie`, `no_feasible` или `insufficient_data`. Это не оценка качества
архитектуры, полезности объяснения или результатов пользовательского исследования.
Пользовательские и экспертные оценки не создаются.

Для воспроизведения отдельного сохранённого результата:

```python
import json
from pathlib import Path
from src.models import Model
from src.explanation import build_explanation

records = json.loads(Path("data/experiment_results.json").read_text(encoding="utf-8"))
saved = records[0]["explanation"]
replayed = build_explanation(Model(**saved["input_snapshot"]))
assert replayed.to_dict() == saved
```

В расчётах нет случайности и текущего времени. При одинаковых входах,
настройках и версиях вычислительных библиотек результаты детерминированы.
